# Security Copilot Agents in Microsoft Purview overview | Microsoft Learn

Microsoft Security Copilot agents are AI-powered processes that help you with specific role-based tasks. Microsoft Purview offers:

- [Microsoft Purview Data Loss Prevention (DLP)](dlp-learn-about-dlp) triage agent
- [Microsoft Purview Insider Risk Management](insider-risk-management) triage agent
- [Data Security Posture Management](data-security-posture-management-learn-about) posture agent in preview
- [Data Security Investigations](data-security-investigations) posture agent in preview

## Data Security Triage Agent

The triage agent provides a managed alert queue where it identifies and prioritizes the highest risk activities. The agent analyzes the content and potential intent involved in the activity based on the organization’s chosen parameters and level of risk tolerance. The agent offers a comprehensive explanation for the logic behind the categorization.

You can find these agents in the **Microsoft Purview embedded experiences**. For more information, see [embedded experiences](/en-us/security-copilot/experiences-security-copilot#standalone-and-embedded-experiences).

Triaging and assigning a priority to alerts can be complex and time consuming. When you set an agent to triage and prioritize alerts, it reduces the amount of time required to complete the task. The agent helps you focus on the most important alerts by sifting them out from the noise of lower risk alerts. This prioritization improves your response time and helps increase the efficiency and effectiveness of your team.

For information on deploying, configuring, and using the triage agents, see:

- [Get started with the Microsoft Purview Triage Agent in Data Loss Prevention](copilot-in-purview-triage-dlp-agent-get-started)
- [Get started with the Microsoft Purview Triage Agent in Insider Risk Management](copilot-in-purview-triage-irm-agent-get-started)

## Data Security Posture Agent

Searching for relevant data and identifying its protection is a time-consuming, tedious, and highly manual task. The agent's primary role is to help you discover sensitive data across your data estate by using a simple natural language-based search. Instead of relying on keyword- or filter-based search tools, it uses large language models (LLMs) to understand user intent. It searches scoped content across your Microsoft 365 ecosystem—including documents, emails, messages, and Copilot interactions—and returns results quickly. The experience includes a concise summary and an associated risk analysis generated by the LLM.

In [Data Security Investigations](data-security-investigations), the Posture agent extends these capabilities to help you proactively discover exposed credentials at scale across your tenant. The agent automates credential scanning across Microsoft 365 data locations, produces AI-generated risk assessments, and tracks tasks on a Kanban-style task board for streamlined review and remediation. For more information, see [Get started with the Data Security Investigations Posture Agent (preview)](data-security-investigations-posture-agent).

For information on deploying, configuring, and using the posture agents, see:

- [Get started with the Posture Agent in Data Security Posture Management](copilot-in-purview-posture-agent-get-started)
- [Get started with the Posture agent (preview) in Data Security Investigations](data-security-investigations-posture-agent)

## Security Copilot agent concepts

Microsoft Purview agents run on Security Compute Units (SCU). Your organization must have SCUs provisioned for the agents to run. For more information, see:

- [Get started with the Microsoft Purview Triage Agent in Data Loss Prevention](copilot-in-purview-triage-dlp-agent-get-started)
- [Get started with the Microsoft Purview Triage Agent in Insider Risk Management](copilot-in-purview-triage-irm-agent-get-started)
- [Get started with the Microsoft Purview Posture Agent in Data Security Posture Management](copilot-in-purview-posture-agent-get-started)
- [Get started with the Data Security Investigations Posture Agent (preview)](data-security-investigations-posture-agent)

The following sections apply only to the Triage agent. They don't apply to the Posture Agent.

### Triggers

Triggers are groupings of parameters whose values must be met for the agent to triage any given alert. Triggers include:

- Time frame: You can define the time scope that alerts are generated in for triaging. See, Select Alert timeframe.
- Custom Instructions: You can define certain instructions for the agent to learn and prioritize from.

### Run automatically or manually

When you deploy an agent, and when you edit triggers, you can select whether the agent runs **automatically based on a set schedule** or **Agent runs manually on one alert at a time** . If you select **Run automatically based on a set schedule**, the agent triages the alerts that are included in the **Select Alert timeframe** setting.

### Select alert timeframe

When you deploy an agent and edit an agent’s triggers, you can pick the timeframe the agent uses to decide which alerts to triage. The options are:

- Only triage new alerts
- Last 24 hours
- Last 48 hours
- Last 72 hours
- Last 7 days
- Last 14 days
- Last 21 days
- Last 30 days

If you select **Only triage new alerts**, the agent only triages alerts that are generated after the agent is deployed. The agent doesn't triage any alerts that were generated before the agent was deployed, which means that all the *Last # hours or days* options are ignored.

If you select any of the *Last # hours or days* options, the agent triages alerts that were generated in the selected timeframe. The selection lets you triage all alerts generated before the agent was deployed. The agent also triages all newly generated alerts.

Important

The timeframe scope for alerts to be triaged is anchored to the moment of successful agent enablement. Essentially, the clock starts ticking when you enable the agent. So, *Last* number of hours or days refers to the time period before agent deployment. ***This timeframe isn't rolling***.

### Agent identity

You can set up agents, including the Posture agent, by using two options:

- **Create and use agent identity (recommended):** Create a separate Microsoft Entra agent identity for the agent. Associate all agent activities with this agent identity. To learn more, see [Microsoft Entra agent identity](/en-us/entra/agent-id/) and [Microsoft Entra agent identities for AI agents](/en-us/entra/agent-id/identity-professional/microsoft-entra-agent-identities-for-ai-agents?branch=main).
- **Assign and use my identity:** Set up the agent by using the identity of the user or admin who sets up the agent. Associate all activities with the user's identity.

Important

Agents aren't [administrative unit aware](purview-admin-units). But if the agent runs in the context of an administrative-unit restricted admin, and there are policies that are administrative-unit scoped to that admin, the agent only sees alerts from the policies that scoped to the admin unit.

### Custom instructions

During the agent configuration process, you can give the agent *custom instructions*. (Custom instructions only apply to the Triage agent in DLP). Microsoft Purview agents use these natural language instructions to enhance alert triage by:

- Translating your input into structured classification logic.
- Running this logic against the document content associated with each alert.
- Raising the alert’s priority if the content matches your custom instruction.

For custom instructions, the agent only analyzes document content, not metadata or behavioral attributes. This means the agent supports content categories like:

- Tax, financial, or legal information.
- Named entities, like credit card numbers, Social Security numbers, and names.
- Logical conditions like *more than five SSNs, contains financial documents*.

If you're unsure whether the condition you want to use is supported, check whether the condition is marked as a content condition. If it is, the agent can use it in custom instructions.

For example, if you enter: *I want to focus on alerts with content that is tax or finance related and contains more than five credit card numbers or SSNs.* The agent interprets this condition as:

```json
{
  "logic_expression": "MATCH(content, 'Tax') or MATCH(content, 'Finance') and (COUNT(content, 'U.S. social security number') >= 5) or (COUNT(content, 'U.S. credit card number') >= 5)"
}
```

## Triaged alerts

The agent triages alerts generated in the timeframe and using policies you select. The agent doesn't triage all alerts.

The agent groups triaged alerts into four categories:

**All**: This category includes all the alerts that the agent triaged. The count indicated in the category might not accurately reflect the true number of alerts until you go into that view and scroll down to load all the alerts. If the conditions that caused the alert to be raised change, or if the alert isn't triaged yet, you can select the alert and then select **Run agent** to manually run the agent on the alert.

**Needs attention**: This category contains alerts that the agent evaluated and determined pose the greatest risk to your organization. When you select one of these alerts, the details flyout opens to show a summary of the alert and other details.

**Less Urgent**: This category contains alerts that the agent evaluated and determined to pose a lower risk to your organization. When you select one of these alerts, the details flyout opens to show a summary of the alert and other details.

**Not categorized**: This category contains alerts that the agent wasn't able to successfully triage. This condition can happen for many reasons, including:

- Server error
- In process of reviewing
- Other error
- Unsupported error for alerts that contain activities that the agent doesn't support.

Agents triage files up to 2 MB in size.

## How agents prioritize

The Triage Agent in DLP prioritizes alerts based on these risk factors:

- Content Risk: This category is the primary risk factor used during agent triage. It covers sensitive content based on Microsoft provided sensitive information types (SIT), trainable classifiers, and default sensitivity labels. For more information, see [default sensitivity labels](default-sensitivity-labels-policies).
- Exfiltration Risk: Exfiltration of sensitive data shared externally.
- Policy Risk: Policy mode and rules with actions affect the prioritization of alerts.
- Content Risk: Label removed or downgraded.

The Triage Agent in Insider Risk Management prioritizes alerts based on:

- Activity risk: The agent identifies activities with the highest risk of exfiltration and reports historical alert insights.
- User risk: Attributes of the user that can affect the prioritization of alerts such as priority user group configuration or number of currently active cases.

### Alert triage details

Important

The Triage agent in DLP only supports alerts from policies that are in active mode. It doesn't triage alerts from DLP policies that are running in simulation mode.

Agents can review alerts that were generated up to 30 days before enablement if the tenant has sufficient SCUs. Alerts that were generated more than 30 days before agent enablement are out of scope.

The Triage agent in DLP triages alerts from Exchange, Devices, SharePoint, OneDrive, and Teams. To triage alerts from Devices, you must enable [evidence collection for file activities on devices](dlp-copy-matched-items-learn).

In DLP, the agent doesn't triage alerts by non-SITs or non-trainable classifier policy conditions only, such as `Email subject match`.

You should do manual analysis on alerts that the agent doesn't evaluate.

### Partially triaged alerts

Here are some examples of situations where you might partially triage alerts.

- DLP rule contains some conditions that aren't supported, such as `The user accessed a sensitive site from Edge`.
- The DLP rule includes certain conditions, but the system can't retrieve the corresponding properties of the email or files, such as `Document couldn't be scanned`.
- User not found.
- During preview, the insider risk management agent analyzes only SharePoint file content. It doesn't analyze email and device activities with accompanying files. If an alert contains only email or device activities, the agent doesn't analyze it.
- An alert generated from a policy that looks only at endpoint or email activities for Insider Risk Management.

### Content analysis

There are some situations where content analysis might be limited.

The content risk prioritization of an alert is based on Sensitive Information Types (SITs), trainable classifiers, and sensitivity labels in content. When an agent evaluates content risk, it only looks for SITs and trainable classifiers that are defined in the policy.

When a DLP alert is associated with fewer than 10 files, the agent scans all the files and uses them to generate the content summary. When an alert includes 10 or more files, the agent uses the potentially top 10 files to generate the file risk summary. In DLP, the triage agent selects the top 10 risky files based on the number of policy classifier hits, the file size, and the most recent file access time. Once this selection is done, the triage agent adds a note stating that the content summary doesn't include all the files in the alert.
